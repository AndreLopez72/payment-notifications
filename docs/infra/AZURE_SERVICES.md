# Azure services and infrastructure rationale

This is a provisional service profile for the assessment workload, not an approved production bill or a deployment authorization. One Azure region serves Mexico, Colombia, and Chile, as required by `SCENARIO.md`. No Azure resources are deployed by this assessment.

|---|---|---|---|

The region list identifies Mexico Central and Chile Central as three-zone regions. Azure SQL General Purpose supports zone redundancy for serverless databases; Service Bus provides zone redundancy in supported regions. The traffic mix makes Mexico Central the stronger provisional single-region candidate in the current proposal, but the assessment provides no latency measurements or legal approval for cross-border processing. Availability-zone resilience does not establish recovery from a full regional outage. See the Microsoft references below.

## Traffic and cost model

The scenario's 30-day peak month is `(26 × 15,000) + (4 × 120,000) = 870,000 notifications`. The month-end burst is 40 notifications/second for 15 minutes, or 36,000 notifications if sustained throughout the interval. The 900,000 active policies are not treated as a notification count. Three broker operations per notification (send, receive, complete) give an indicative `870,000 × 3 = 2.61M Service Bus operations/month`; retries, locks, DLQ handling, replay, and additional consumers increase this number.

The provisional priced portion is about **`$285–$794/month` for SQL compute plus Standard Service Bus base**, before Key Vault operations and the excluded items above. The Premium network fallback adds about `$734/month` over the Standard base in this price reference. These are order-of-magnitude list-price estimates, not a complete bill, budget approval, or capacity guarantee. They use public USD retail rates and may differ by date, offer, currency, and agreement. This is not a like-for-like total-cost comparison across eligible regions; region selection must be revisited if the full regional service bill or latency measurements favor another location.

The proposed SQL upper bound is deliberately limited to 2 vCores to control spend, but the documented burst and Salesforce availability/API constraints mean the system's actual bottleneck may be elsewhere. Run a representative load test before treating the profile as adequate. If 2 vCores fail the latency/freshness objectives, raise the ceiling only to the smallest measured capacity that passes; if traffic remains higher on average, compare provisioned General Purpose against serverless using measured utilization. Do not reduce zone redundancy without an explicit resilience decision.

## Infrastructure and deployment boundary

Terraform keeps region, SQL capacity, Service Bus SKU/network mode, IP allowlist, Key Vault settings, identity IDs, and platform resource IDs as environment inputs until owners approve them. The current IaC models the Standard profile with IP filtering and no Service Bus private endpoint; the Premium fallback disables public access and uses a private endpoint. SQL and Key Vault use private endpoints in either profile. The latest Terraform edits still need formatting and provider-schema validation before anyone relies on a plan.

Existing private endpoint subnet, private DNS zones, Log Analytics workspace, Entra tenant, workload principals, and state backend are inputs owned by the platform. The infrastructure code does not create Azure compute: Mule 4 remains on the enterprise integration platform selected by the solution design. No deployment is authorized or performed by this assessment.
