## Validation

- Compared the design and ADRs with `README.md`, `SCENARIO.md`, `TASKS.md`, `SUBMISSION_CHECKLIST.md`, the provider webhook specifications, Salesforce data model/API constraints, and the incident record.
- Compared the proposed Part B webhook fields and signature headers with the Quetzal and Andina specifications and samples. Parsed `premium-payment.schema.json` with PowerShell `ConvertFrom-Json`. No YAML parser was available locally, so `webhooks.openapi.yaml` received a manual structural review only; it has not been automatically linted or imported into API Manager.
- Compared both provider verifiers and test setup with their supplied signing rules, timestamps, samples, and vectors. The canonical schema validation and MUnit cases were authored. Maven was attempted with Java 17.0.21.1 and Maven 3.10.1 but could not resolve the Mule Maven Plugin because the default local repository was not writable and the retry failed JVM TLS certificate validation; compilation and MUnit remain unverified.
- Parsed the Mule XML files and relevant JSON files, confirmed all copied provider fixtures byte-for-byte, and independently recalculated all seven supplied HMAC vectors. These checks do not substitute for compiling or running MUnit.
- Traced the HTTP listener variables into the DataWeave mappings and found that the listeners did not assign the required `receivedAt` value. Both listeners now capture one receipt time and derive signature-window epoch seconds from it. This source-level correction still requires Mule/MUnit execution.
- Checked Maven repository access after the candidate clarified that only a free MuleSoft learning account is available. Removed the Enterprise credential configuration from CI and configured the three public repositories listed in MuleSoft's Maven reference. Artifact resolution and a successful CI run remain unverified.
- Consulted official MuleSoft documentation for runtime/Java compatibility, HTTP Connector, Java Module, Mule Maven Plugin, DataWeave cryptography, hexadecimal encoding, UTC timezone conversion, and MUnit configuration. The selected versions and runtime pairing are recorded as provisional in `docs/ASSUMPTIONS.md` (A-24).
- Checked that the proposal preserves the assessment scope: Mule 4 as the reference stack, all three countries in Part A, Mexico and Colombia only for Part B, no direct policy-status writes, no deployment, and no real external calls.
- Rechecked the Salesforce call estimates against the documented 200-record batch size, 150,000-call integration budget, 25-request concurrency limit, and the proposed two-second batch linger. The estimate is labeled as a sizing estimate, not a proven SLO.
- Rechecked provider-specific signature and retry identity behavior against the webhook references. The design preserves the distinction between provider event identity and Meridian's per-ingestion attempt ID.
- Reviewed the resulting files and searched for key terms and decisions. The Mule and MUnit XML descriptors and JSON schema/manifest parse successfully. The build and MUnit suite remain unverified because Maven dependency resolution is blocked by JVM TLS certificate validation. The practical README records this result, the fail-closed ports, and remaining runtime gaps.
- The final selection remains Mule 4, Azure SQL, Azure Service Bus, and the scenario's existing Azure Monitor, Application Insights, and Log Analytics. These architecture choices are proposals and are listed in `docs/ASSUMPTIONS.md` where the source documents do not dictate them.
- Reviewed Part C resource and workflow files against `TASKS.md`, `SCENARIO.md`, the solution design, and assumptions. Terraform 1.9.8 formatting and backend-disabled initialization passed; local validation stopped before configuration checks because the AzureRM provider failed its local gRPC TLS handshake. `actionlint` v1.7.10 passed on both workflow files. GitHub CI exposed Terraform schema and Mule Maven dependency errors; their code/configuration changes await a successful rerun. No Azure deployment was triggered. `docs/infra/AZURE_SERVICES.md` contains an illustrative cost estimate with explicit exclusions and unapproved inputs.
- Compared the Part D runbook with `SCENARIO.md`, `SOLUTION_DESIGN.md`, `INC-0412.md`, and assumptions. The cause statement is limited to what the `400 INVALID_FIELD` samples and retry/DLQ counts support; policy-reference ownership and the v1 replay tool remain open. No production action or message replay was performed.
- Checked each Part E finding against the added lines in `PR-214.diff` and the cited provider/Salesforce references. The review is a document analysis only; no code was changed in the teammate's PR and no test suite was run.
- Reviewed the submission checklist and marked only present deliverables as complete. Candidate-specific fields, repository visibility, repository-wide secret/history review, and successful Mule/Terraform validation remain outstanding.

## What I discarded or corrected

- Did not switch observability to Dynatrace. It appeared in additional employer-stack information, while the assessment scenario explicitly identifies Azure Monitor, Application Insights, and Log Analytics as existing platform services. The assessment guidance was given priority.
- Did not select Spring Boot, Azure Functions, Container Apps, App Service, or AKS as the implementation runtime. They were discussed as alternatives or company technologies; the documented proposal uses the assessment's Mule 4 reference stack and the existing Mule-capable integration platform.
- Corrected the peak Salesforce-call estimate to account for the proposed two-second batch linger: approximately 450 calls during the 36,000-notification burst at 40 notifications/second when batches average about 80 records, versus 180 calls if full 200-record batches are achieved. The daily hard upper bound is separately stated as 120,000 calls if every notification were sent individually.
- Marked unresolved architecture values as assumptions or validation items instead of presenting them as facts from the assessment. These include retention, key derivation, retry limits, and the Mule platform's identity support for Azure access.
